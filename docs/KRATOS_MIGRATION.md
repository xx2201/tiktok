# Kratos 迁移记录

## 目标与顺序

用户要求：先把整个项目迁移为 Kratos，修复已确认的问题，验证后提交 Git；再选一个真实业务需求，结合需求分析、产品规则、技术方案、任务拆分、开发、测试、验收、发布和反馈讲解完整开发流程。

业务教学阶段必须在迁移提交完成后开始。当前候选需求为「收藏视频，方便以后回看」，其规则和方案届时单独确定。

## 迁移范围

- HTTP 网关和 user、video、favorite、comment、relation、message 六个服务迁移至 Kratos v2.9.2；RPC 使用标准 Protobuf/gRPC。
- 保留现有 `/douyin` 接口、六个业务服务边界、MySQL 表名以及 MinIO 媒体存储；点赞和关注仍使用 RabbitMQ、Redis 和异步落库。
- `api` 保存协议；`internal/server` 处理传输；`internal/service` 转换协议；`internal/biz` 定义业务和仓储接口；`internal/data` 实现仓储。
- 将数据库连接、迁移、队列消费者和后台任务移出包 `init`，由应用显式创建并关闭资源。
- 删除替换后的 Hertz、Kitex、Gin 代码和相关旧依赖，不保留旧框架适配层。
- 更新构建、启动、容器配置和项目文档。

## 验证与完成标准

1. 七个应用均能构建；全项目测试和静态检查通过。
2. 在真实 Kratos HTTP/gRPC 传输中验证参数、token、JSON 数字/布尔值、错误传播和所有现有路由。
3. 验证注册登录、Feed 分页、发布、点赞/关注、评论授权、朋友列表和聊天规则；验证重复动作和失败路径。
4. 对数据库事务、Redis 状态合并和消息消费补充必要验证，明确哪些证据来自实际组件、哪些来自隔离测试。
5. 独立检查工作区和待提交内容，提交迁移代码；原有未跟踪 `.ua/` 和 `docs/UA_ONBOARDING.md` 保留，避免把过期图谱当作新架构依据。

## 本次检查发现

- 评论删除用 `||` 拒绝权限，实际要求是评论作者或视频作者任一可以删除。
- 评论列表把浏览者 ID 当作评论作者 ID，关注状态判断和背景图对象名也不正确。
- 多个 HTTP handler 忽略 RPC error，之后直接访问响应。
- Feed handler 丢失 `next_time`；业务游标使用 `UpdatedAt`，数据库排序使用 `CreatedAt`。
- Redis 读键过期而写键存在时，代码仍拆分读键内容，存在越界风险；同步过程中删除键可能丢弃新动作，数据库失败时也会删除待写状态。
- RabbitMQ 重连分支未重新发布消息便返回成功。
- 私信发送只检查单向关注，却声明必须朋友关系；`pre_msg_time` 未作为轮询游标使用。
- 工具包导入了不同模块路径；SHA256 实现没有返回实际写入内容的摘要；RSA 类型断言和文件资源管理缺少检查。

以上来自迁移前源码检查。旧的无调用加密工具已删除，没有另造兼容实现。

## 验证记录

- go build ./...、go vet ./...、go test -race ./... 已通过。
- Kratos HTTP → gRPC 实际传输测试通过：16 条路由、query/multipart 绑定、数字 ID、显式 false、Feed 游标、错误码与限流。
- 首轮真实组件验收通过：七个应用通过 etcd 发现，注册登录、FFmpeg 截帧、MinIO 视频/封面读取、点赞/取消、评论权限、双向关注、私信加密及历史/增量读取、视频失败补偿。
- 真实 MySQL/Redis 验证通过：20 个并发重复动作只计数一次；旧动作不覆盖新状态；写入失败事务回滚并保留 Redis 待写内容；同步清理不删除后来到达的动作。
- 首轮联调发现请求日志含敏感字段，已用 Kratos 日志过滤器隐藏 args，并去除 FFmpeg 错误中的签名 URL。
- 复验时 Docker engine、安装目录及 CLI 先后不可见。最新默认媒体初始化与完整组件复验、通用应用 Docker 镜像构建，须恢复 Docker 后确认。首轮结果不构成随后改动的运行证据。

## 交付边界

七个应用已完成源码迁移，没有 TODO、占位 handler 或旧框架适配层。CI 配置已写入，未推送或触发远端 CI。生产部署、压测、旧数据升级与灾难恢复没有执行。

主要限制见 README：MD5 密码格式、进程内视频任务、异步动作与 Redis 序号恢复、时间游标、RSA 明文长度、内部明文 gRPC。不能宣称框架迁移解决了全部生产问题。
